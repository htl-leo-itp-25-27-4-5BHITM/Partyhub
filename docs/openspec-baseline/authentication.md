# Authentication and identity contract review

Step 2, inspected and integrated 2026-09-23 from source revision `9487ccb90bb438e24b3cfab547a5dc900b11aecb`. No tracked application source was changed by this documentation/specification stage. This review separates the **accepted** AUTH-01-AUTH-12 contract in [user-auth-and-identity](../../openspec/specs/user-auth-and-identity/spec.md) from **observed** source. It does not certify running clients or a deployment.

Read alongside [endpoint access](access-matrix.md), [environment evidence](auth-environments.md), [coverage](coverage.md), [decisions](decisions.md) and [gaps](gaps.md). AUTH-01 through AUTH-09 retain their stable coverage IDs; AUTH-10 through AUTH-12 add public bootstrap and the bounded iOS login/session minimum. Browser requirements do not prescribe iOS storage, and AUTH-12 does not promise provider logout.

## Browser flows

The accepted browser/backend contract is D001-D003/D014 and AUTH-01-AUTH-10. The following success and failure scenarios are review criteria tied to those requirements, not claims of executed tests.

| Flow | Observed source | Success scenario and requirement | Failure / boundary scenario and disposition |
|---|---|---|---|
| Login | B1 loads issuer from public config, builds `frontend` authorization URL, generates random state/nonce/verifier and S256 challenge, records transaction in tab session storage, redirects to Keycloak. No password grant or `keycloak-js` in this path. | **B-LOGIN:** When login starts, generate transaction values and authorize with code/PKCE (AUTH-04); after completion resolve the PartyHub user (AUTH-01). | **B-CONFIG:** Failed public-config fetch retains same-origin issuer fallback; this is an observation, not an availability guarantee. **B-DENIED:** Provider error reaches callback error UI; no authenticated session may be established (AUTH-04/05). |
| Callback | B1 checks provider error, code/state and saved state before exchange; matching code exchanges with verifier and callback URI. Present ID-token nonce is compared; missing nonce is not rejected. B2 displays errors. | **B-CALLBACK:** Matching transaction permits code exchange, stores tokens, calls `/api/users/me`, then returns to intended path (AUTH-04/01). | **B-STATE:** Missing/mismatched state or absent transaction clears state; mismatched transaction redirects to login without exchanging code (AUTH-04). **B-EXCHANGE:** Non-OK token response clears session. **B-NONCE:** Wrong present nonce is rejected; absent nonce/ID-token validation hardening remains G022, not proof of complete OIDC validation. |
| Registration and onboarding entry | B1 `register` uses the Keycloak registrations endpoint, PKCE and a login-page redirect; B2 login page displays flags then offers a fresh login. Realm email-verification flags differ by environment. | **B-REGISTER:** Account registration belongs to Keycloak; a later successful authenticated lookup links/creates a PartyHub user under AUTH-03/08. Creating a local database user alone is not login (AUTH-02). | **B-REGISTER-RETURN:** Login page does not exchange the returned registration code; fresh login is the observed continuation. Flags are set before registration/verification is confirmed and are not trustworthy success evidence (G025). No accepted requirement promises mandatory email verification in every environment. |
| Storage and page initialization | B1 stores access/refresh/ID tokens, expiry and current-user cache in `sessionStorage`; clears legacy localStorage identity keys. `init` refreshes and loads user when missing. B2 numeric compatibility helpers manipulate display/cache data. | **B-RESTORE:** Same-tab navigation restores session before protected logic (AUTH-05/06). Cached numeric ID never authenticates a backend request (AUTH-02). | **B-NO-SESSION:** Without usable session, protected page starts login (AUTH-01). **B-CLEAR:** Logout or invalid authentication removes token/current-user/transaction keys (AUTH-06). Cache setters and profile IDs do not prove authentication. |
| Protected page and API entry | B3 add/edit scripts await `requireAuth`; notifications requires login; own-profile branch requires login if no current user. Party list initializes with optional login. B1 attaches bearer through shared facade; public callers can choose `authRequired:false`. | **B-API:** Protected calls refresh if needed and attach bearer (AUTH-05/09); public browsing does not create caller authority. | **B-NO-TOKEN:** Protected call without bearer starts login and returns a synthetic 401 rather than sending the protected request (AUTH-02/05). Route guards are client UX; every backend still needs the checks in the access matrix. This is bounded entry-point evidence, not an exhaustive UI execution claim. |
| Refresh | B1 uses 30-second pre-call threshold (10 seconds at init), refresh-token grant and replacement session. Non-OK response or missing refresh clears auth. | **B-REFRESH:** A near-expiry token refreshes before protected request (AUTH-05). Thresholds are observed implementation details, not new product requirements. | **B-INVALID-REFRESH:** Invalid provider session requires clearing state and login (AUTH-05). A transport/JSON exception propagates without the same cleanup; no retry/error contract is fully specified (G021). |
| User resolution and onboarding | B1 calls `/api/users/me` with bearer after code exchange; caches returned user and numeric ID for UI use. Backend behavior is S1 below. No dedicated onboarding-required response is handled. | **B-ME:** Valid linked/new user response supplies acting-user context (AUTH-01/08); user creation remains a backend decision. | **B-ME-FAIL:** 401/403 clears local auth; other non-OK results return null while callback still redirects, and network errors propagate. Consistent failed-lookup recovery needs G021. AUTH-08 permits explicit onboarding as an alternative; no such runtime flow was found. |
| Logout | B1 clears local state, navigates to realm logout with client ID, post-logout URI and ID-token hint when available; B2 logout page invokes it. | **B-LOGOUT:** Local credentials disappear and provider logout is requested (AUTH-05/06). | **B-LOGOUT-FAIL:** Local state stays cleared if provider navigation fails; provider-session termination was not exercised. Cached identity must not restore protected access (AUTH-02/06). |

## iOS flows

Native implementation exists and AUTH-10-AUTH-12 now define the accepted public-bootstrap, native-login and token-backed-session minimum while retaining shared backend AUTH-02/07/08/09 rules. Source mismatches remain recorded as gaps rather than being treated as implementation fixes.

| Flow | Observed source | Accepted success scenario | Failure / boundary scenario and disposition |
|---|---|---|---|
| Login and registration entry | N1/N2 use `partyhub-ios`, `partyhub.auth://callback`, authorization code/S256 PKCE and ephemeral `ASWebAuthenticationSession`. N3 exposes one Sign in button; registration is available through the provider, not a separate native form. | **N-LOGIN:** Use provider web authentication and a fresh PKCE/state transaction; PartyHub does not collect the provider password. | **N-CANCEL:** Cancellation leaves signed-out entry usable without a new authenticated session; LoginView suppresses cancellation error text. Other startup/provider errors are displayed. No terms acceptance or email-verification policy is inferred from labels. |
| Callback and exchange | N1 verifies provider error, state and presence of code before exchange. Generates nonce but does not pass expected nonce to callback or model it in ID-token claims. | **N-CALLBACK:** Matching callback exchanges code with original verifier/redirect and proceeds to backend lookup. AUTH-11 makes transaction and nonce binding explicit. | **N-STATE:** Mismatch/missing code/provider error must not exchange/store a new session. **N-NONCE:** Native nonce binding is absent; G022 records this gap against AUTH-11. Decoding a JWT payload is not signature validation. Backend bearer validation remains mandatory (AUTH-07). |
| Token storage and user lookup | N1 calls bearer `/api/users/me` before writing new tokens, subject, PartyHub ID and display-name fallback. N2 stores them in Keychain with `AfterFirstUnlockThisDeviceOnly`; decoded claims are presentation hints. | **N-ME:** Successful backend lookup binds PartyHub ID to the token; **N-STORE:** persist native credentials in Keychain, keeping browser sessionStorage rule browser-specific. | **N-ME-FAIL:** Lookup/non-2xx/decoding error does not establish a new session; **N-STORAGE-FAIL:** partial sequential Keychain writes can fail and need recovery review (G023). Numeric IDs alone do not authorize APIs (AUTH-02/08). |
| Bootstrap and refresh | N1 loads Keychain once, sets `sessionEstablished` from token+ID presence, and refreshes expired access token only if refresh exists. N2 treats expiry with 30-second margin. Refresh task coalesces concurrent requests. | **N-RESTORE:** Restore a usable session; **N-REFRESH:** obtain a usable token before protected API calls and save replacement in Keychain (AUTH-12). | **N-EXPIRED:** `validAccessToken` clears when refresh missing/fails. Bootstrap can leave expired token+ID with no refresh in an established UI state; G023. `issuedAt:nil` uses current time in expiry calculation, another restoration review case. AUTH-12 does not allow session validity to rely on cached ID alone. |
| API access | N3 `.bearerToken` calls `validAccessToken`; `.bearerOrAnonymous` omits bearer on token failure; `.none` adds no auth. API 401 becomes an error, not automatic provider logout. | **N-API:** Protected requests use validated-current bearer and linked acting user (shared AUTH-02/07/09). | **N-PUBLIC:** Optional anonymous fallback is suitable only for public operations in the matrix. **N-UNAUTHORIZED:** Protected calls must not fall back to numeric identity. Session expiry/401 UX beyond observed behavior remains a remediation case, not runtime proof. |
| Logout | N1 clears four Keychain accounts and in-memory identity/session flag; N3 root switches to LoginView, stops polling/clears badges. Config defines provider logout endpoint but `logout` does not use it. | **N-LOGOUT:** AUTH-12 requires explicit native logout to remove local credentials and current-user context; browser provider-logout behavior is not imposed on iOS. | **N-LOGOUT-FAIL:** Keychain remove errors are suppressed in source, so durable deletion is unverified (G023). Native provider-session termination/revocation is unresolved Q013; local logout does not claim either. Local party/visit cache lifecycle belongs to Steps 10–11. |
| Linking/onboarding and legacy deep links | Same S1 backend as browser. N3 routes `partyhub://login?userId=` to a legacy notification; OAuth callback has separate scheme. No native onboarding-required screen was found. | **N-LINK:** Token-backed `/me` uses shared link/create contract (AUTH-08/11). | **N-LEGACY:** Numeric QR/deep-link input is not Keycloak authentication (AUTH-02); retained QR behavior is Q001/Step 9. **N-ONBOARD:** An explicit onboarding result cannot be treated as a completed PartyHub session under AUTH-11; current client only accepts a response with `id`. |

## Backend identity and onboarding

S1 applies to browser and iOS bearer callers, including optional authenticated reads. The accepted sequence is subject link, one matching unlinked account, then minimal user creation or explicit onboarding (AUTH-08 / D003). Numeric input alone is never an accepted credential (AUTH-02).

| Case | Accepted success/failure criterion | Source observation / disposition |
|---|---|---|
| Existing subject | **S-LINKED:** Valid token subject resolves its stored Keycloak link. | Resolver first tries parsing subject/principal as a numeric local ID, before Keycloak-ID lookup. This ordering is not conditioned on bypass and can select a different record for a numeric subject (G019). No live collision was reproduced. |
| One unlinked match | **S-MATCH:** One unlinked user matching token username/email may be linked to that subject. | Repository lowercases/trims username/email, also matches distinctName, and limits results to one. It does not count ambiguous matches or check `email_verified`; claim-trust/ambiguity policy remains Q012/G020. Existing AUTH-08 does not authorize arbitrary selection among multiple matches. |
| No match | **S-NEW:** Create minimal user from claims or respond with explicit onboarding required. | Source chooses creation, with username/principal/subject fallback, distinctName/displayName/email, default notification settings and welcome-email call. Existing link reuse does not create another user; welcome delivery guarantees belong to Step 8. There is no dedicated onboarding response in the inspected resolver. |
| Missing/invalid credential | **S-REJECT:** Reject protected action without a valid bearer, including numeric-only headers/query values (AUTH-02/07). | `@Authenticated` plus framework JWT mechanism and resolver supply normal path; bypass can create identity from any nonblank header (G002). Optional resolver returns empty for anonymous identity. See environment evidence for profile distinctions. |
| Wrong actor / object | **S-ACTOR:** Derive actor from token; retain domain ownership/visibility checks (AUTH-09, D007). | Changing a path/body/query ID must not impersonate another actor. A valid identity alone is not host or recipient authority; each matrix row traces actual object checks and missing policy. |
| Missing claims, ambiguous link, persistence/provider failure | **S-UNRESOLVED:** Do not claim the existing happy-path scenarios specify all failure statuses or onboarding UI. | Fallbacks are observed, not approved uniqueness/recovery policy. Q012 owns linking ambiguity; G013 records missing execution evidence. Concrete status/schema reconciliation belongs to Step 11, with identity decisions retained in Step 2 follow-up. |

## Coverage and completion disposition

All 12 accepted requirements and 43 scenarios are indexed in [coverage.md](coverage.md#user-auth-and-identity). This document supplies platform-specific flow success/failure cases and the linked matrix/environment observations. T1 asserts existing-subject lookup, unlinked-user matching via a synthetic principal, and minimal creation; it does not test signed JWTs, browser PKCE, native callbacks, real claims, uniqueness or logout. No application tests, login sessions or deployment commands were run.

The bounded child delta is integrated into the main identity spec, preserving the existing browser/JWT/linking scenarios and keeping unresolved endpoint policy with its domain owners. Group 2 can close because AUTH-10-AUTH-12 define the accepted minimum; Q011-Q013 and G019-G023 remain explicit follow-up limits rather than silent product guarantees.
