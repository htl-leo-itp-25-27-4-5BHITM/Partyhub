1 · Warum?

„Bei mir funktioniert's!“

Ohne Automatisierung

  1. Jemand merged auf main
  2. Jemand baut das Projekt lokal am Laptop
  3. Docker-Image per Hand hochladen
  4. kubectl per Hand auf dem Server
  5. Merken, dass die Tests gar nicht liefen 😬

Mit CI/CD

  1. Merge auf main
  2. Alles Weitere läuft automatisch
  3. Immer dieselben Schritte
  4. Immer in einer sauberen Umgebung
  5. Nichts geht live, wenn ein Test rot ist
Links das typische Problem: viele manuelle Schritte, jeder macht es ein bisschen anders, Fehler fallen spät auf. Klick: rechts dasselbe mit CI/CD. Die Pipeline macht es jedes Mal gleich.
2 · Was ist CI/CD?

Drei Begriffe, die aufeinander aufbauen

🔁

Continuous Integration

Jede Änderung wird automatisch gebaut und getestet, sobald sie ins gemeinsame Repo kommt.

„Funktioniert mein Code mit dem der anderen?“

📦

Continuous Delivery

Nach grünen Tests entsteht automatisch ein auslieferbares Paket. Ausrollen per Klick.

„Wir könnten jederzeit ausliefern.“

🚀

Continuous Deployment

Das Paket wird ohne manuellen Schritt in Produktion ausgerollt.

„Jede grüne Änderung ist sofort live.“

CI: Integration, also Zusammenführen und Testen. Delivery: Es gibt immer ein fertiges Paket, aber ein Mensch drückt den Knopf. Deployment: Auch der Knopf ist automatisiert. Die beiden CD unterscheiden sich nur im letzten Schritt.

2 · Was ist CI/CD?

Teil des DevOps-Kreislaufs

CI/CD ist der automatisierte Teil eines Kreislaufs, der sich bei jeder Änderung wiederholt. Grün: Build und Test, das ist CI. Pink: Release und Deploy, das ist CD. Danach Betrieb und Feedback, daraus entsteht die nächste Planung.
2 · Was ist CI/CD?

Warum sich das lohnt

🐞 Fehler früh finden

Kaputter Code fällt im Pull Request auf, nicht erst auf dem Server.

🤖 Keine Handarbeit

Niemand baut lokal, lädt Images hoch oder tippt kubectl.

🔎 Nachvollziehbar

Jedes Image trägt den Commit-SHA, aus dem es gebaut wurde.

⚡ Kleine, häufige Releases

Bei uns gehen oft mehrere Änderungen pro Tag live.

Vier Vorteile. Am wichtigsten für uns als Team: Fehler fallen im Pull Request auf, und niemand muss sich merken, wie man deployt.

3 · Unsere Pipeline

Drei Workflows hintereinander

test.yml

Test

  1. Browser-Tests node --test
  2. Postgres und Keycloak starten
  3. mvn clean test
  4. Quarkus starten
  5. API-Tests api/*.http
push.yaml

Build and Push

  1. getesteten Commit auschecken
  2. Tag = Commit-SHA
  3. mvn package
  4. Image partyhub-backend
  5. Image partyhub-keycloak
deploy.yml

Deploy

  1. Kubeconfig aus Secret
  2. Keycloak-DB-Check
  3. kubectl apply k8s/
  4. kubectl set image
  5. rollout status

Build and Push startet nur, wenn Test auf main grün war. Bei Pull Requests heißt es „skipped“.

Test läuft bei jedem PR: zuerst Frontend-Tests, dann Datenbanken und Keycloak per Docker Compose, dann die Maven-Tests und zum Schluss die API-Tests gegen einen echten Quarkus. Build and Push baut genau den getesteten Commit, taggt ihn mit dem Commit-SHA und pusht zwei Images. Deploy holt sich die Zugangsdaten aus einem GitHub-Secret, prüft, dass die Keycloak-Datenbank migriert ist, damit keine Konten verloren gehen, und rollt die neuen Images aus. Datenbanken und Uploads bleiben erhalten.
3 · Unsere Pipeline

Unser Ablauf im Team

  1. Eigenen Branch anlegen, lokal ./mvnw clean test und ./run-http-tests.sh
  2. Pushen und Pull Request auf main öffnen. Die CI läuft automatisch.
  3. Rot → im Branch korrigieren · Grün → Review im Team → Merge
  4. Pipeline baut und deployt. Nach ca. 9 Minuten ist die Änderung live.
Nie direkt auf main arbeiten. Jede Änderung kommt über einen eigenen Branch und einen Pull Request. Erst wenn die CI grün ist und jemand reviewt hat, wird gemergt. Der Merge ist gleichzeitig das Deployment.

Ein Beispiel, bei dem etwas schiefging. Der Test für PR 228 war rot: Der Keycloak-Container ist abgestürzt, weil das Dev-Realm nicht importiert werden konnte. Der PR wurde trotzdem gemergt, das geht, weil main nicht geschützt ist. Auf main war der Test wieder rot, deshalb liefen weder Build noch Deploy, und die Produktion blieb auf der alten Version. PR 231 hat den Fehler behoben, danach lief alles durch. Fazit: Die Pipeline hat die Produktion geschützt, aber nicht main selbst.

5 · Umsetzung

So baut man so eine Pipeline auf

  1. Voraussetzungen: Git-Repo, automatische Tests, Build mit einem Befehl (./mvnw)
  2. CI-Workflow: test.yml bei pull_request und push
  3. Container: Dockerfile und Registry ghcr.io
  4. Zielumgebung: Manifeste in k8s/, Kubeconfig als GitHub-Secret
  1. Deploy-Workflow: verknüpft über workflow_run / workflow_call
  2. Absichern: Branch-Schutz, Required Checks, concurrency
  3. Team-Regeln: Branch → PR → Review → Merge
So wurde unsere Pipeline aufgebaut, und so geht man bei jedem Projekt vor. Ohne automatische Tests bringt CI nichts, deshalb sind sie die Voraussetzung. Geheimnisse wie die Kubeconfig kommen als Secret in die GitHub-Einstellungen, nie ins Repo. Schritt 6, das Absichern, ist bei uns noch nicht ganz fertig.
5 · Umsetzung

Ein minimaler CI-Workflow


# .github/workflows/test.yml
name: Test
on:
  pull_request:
    branches: [ "main" ]
  push:
    branches: [ "main" ]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with: { distribution: temurin, java-version: '21' }
      - run: mvn clean test

on

Wann läuft der Workflow? Bei PRs und Pushes auf main.

runs-on

Auf einer frischen Ubuntu-VM von GitHub.

steps

Code holen, Java einrichten, Tests ausführen. Ein roter Schritt = roter Lauf.

So sieht ein CI-Workflow im Kern aus. Auslöser, Umgebung, Schritte. Unser echter test.yml ist länger, weil er zusätzlich Datenbanken, Keycloak und die API-Tests startet, aber das Prinzip ist dasselbe. Mit Pfeiltaste durch die Markierungen klicken.

5 · Umsetzung

Branch-Schutz einrichten

GitHub → Settings → Branches → Ruleset für main

  • ✓ Require a pull request before merging
  • ✓ Require status checks to pass: test
  • ✓ Block force pushes
  • ✓ Restrict deletions

Braucht Admin-Rechte im Repo. Vorher im Team absprechen.

Danach gilt:

Pull Request
→
Test grün?
→
Review?
✓ Merge → automatischer Deploy
✗ Merge-Button gesperrt 🔒
Mit diesen vier Einstellungen kann niemand mehr direkt auf main pushen, und ein PR lässt sich nur mergen, wenn der Test grün ist. Genau das hätte Beispiel B verhindert. Wichtig: Der Test läuft bei jedem PR, auch bei Doku-Änderungen, deshalb blockiert der Required Check keine Doku-PRs.

CI

CD

Das Ergebnis wird automatisch verpackt und ausgerollt.

PartyHub

test.yml → push.yaml → deploy.yml. Vom Merge bis live ca. 9 Minuten.

Branch-Schutz, damit roter Code gar nicht erst auf main landet.
